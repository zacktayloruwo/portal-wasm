# Census Discovery Portal (static)

A static, browser-only port of the Census Discovery Portal Shiny app. The
inventory lives in two parquet files that are queried **in the browser** with
[DuckDB-WASM](https://duckdb.org/docs/api/wasm/overview). There is no server:
the site is plain HTML, CSS and JavaScript hosted on GitHub Pages.

Live site: https://zacktayloruwo.github.io/portal-wasm/

## Develop

```bash
npm install
npm run dev        # http://localhost:5173/portal-wasm/
npm run build      # writes dist/
npm run preview    # serves dist/ for a final check
```

`BASE_PATH=/ npm run build` builds for a root domain instead of the
`/portal-wasm/` project path (see `vite.config.js`).

Append `?selftest` to the URL to run the queries in `public/data/selftest.json`
against DuckDB-WASM and print pass/fail to the browser console
(`window.__selftest` holds the table). Keyword cases are also run through the
app's own keyword search and must give the same results.

After the engine has loaded, the page sets `data-engine="ready"` on the
`<html>` element, which is handy for timing tests.

## How it works

### Data files

Everything the app needs is in `public/data/`, generated by `prep/prep_db.R`
in the project's data-preparation folder (see [Update the data](#update-the-data)).

| File | Contents | Loaded |
|---|---|---|
| `inventory_en.parquet`, `inventory_fr.parquet` | one row per inventory item, 27 columns; nine of them are `VARCHAR[]` lists (subject, years, formats, …) plus two new list columns `access_urls` / `access_labels` | current language at boot, the other in the background once the page is idle |
| `meta.json` | version strings, every interface translation, and one entry per database column (EN/FR header, whether it is a list, whether it appears in results / detail, and the tooltip definition) | at boot |
| `viz_counts.json` | pre-aggregated counts for the Visualize tab | first visit to the tab |
| `snapshot_en.json`, `snapshot_fr.json` | the opening view: first 25 records in the default order, the record count, and every search field's choices (about 6 KB compressed) | at boot, for the current language |
| `selftest.json` | query fixtures with the counts R's DuckDB produced | only with `?selftest` |

Compared with the Shiny app's 67 MB DuckDB file, each parquet is about 1.2 MB.
The pre-rendered `access_link` HTML column was dropped and is rebuilt in the
browser from the two URL/label lists, and the raw `itemAccess` link text is
dropped too, since `access_urls` holds the same URLs.

The DuckDB-WASM engine itself is the largest download (about 6.8 MB). `db.js`
loads it from jsDelivr, pinned to the installed package version, because
jsDelivr serves it Brotli-compressed (about 1 MB smaller than GitHub Pages'
gzip) and lets browsers cache it for a year. If jsDelivr cannot be reached,
the self-hosted copy built into `dist/assets` is used instead.

Reading parquet also needs DuckDB's parquet extension, which is not built
into the engine. Rather than letting the engine fetch it from
`extensions.duckdb.org`, the site serves its own copy from
`public/duckdb-ext/<DuckDB version>/<wasm_eh|wasm_mvp>/` (the path layout
DuckDB expects), and `db.js` points DuckDB's extension repository there and
loads it as soon as the engine starts. These are DuckDB's own signed files,
committed to the repo. After upgrading `@duckdb/duckdb-wasm`, refresh them
with

```bash
node scripts/fetch-duckdb-ext.mjs v1.4.3   # the new DuckDB version, from SELECT version()
```

If the copy for the running DuckDB version is missing, `db.js` logs a
console warning naming the command to run and falls back to
`extensions.duckdb.org`, so the app keeps working.

### Start-up sequence

`src/main.js` is arranged so the visitor sees results before the search
engine has finished loading:

1. As soon as the script runs, it starts the two large downloads side by
   side: the DuckDB-WASM engine (in a Web Worker, `db.js`) and the parquet for
   the current language. The language is taken from `?lang=`, then
   `localStorage`, then defaults to English. When both have arrived the
   parquet is copied into an in-memory table, `inventory_en` or
   `inventory_fr`.
2. Meanwhile it fetches `meta.json` and `snapshot_<lang>.json`, initialises
   translations (`i18n.js`) and builds the five tab panels. Each factory
   (`search_cv.js`, `search_kw.js`, `visualize.js`, `markdown.js`) appends its
   own DOM to an empty `<section>` in `index.html` and returns a small
   controller (`refresh`, `reset`, `showSnapshot`, `activate`, `load`).
3. It shows the snapshot (the first page of results and every field's
   choices) and hides the overlay. Without a snapshot it waits for the engine
   and runs the first query instead.
4. It starts the hash router (`router.js`). The URL hash names the tab
   (`#search`, `#search_kw`, `#visualize`, `#documentation`, `#about`), so
   tabs are bookmarkable and the back button works.

Every query goes through `db.query()`, which waits until the engine and the
first table are ready, so anything the visitor does early (choosing a filter,
paging, opening a record) simply shows the results spinner until then. A
failure in any step is written into the overlay instead of leaving a blank
page.

### Modules

```
src/
  main.js        boot sequence, EN | FR switch, cross-tab reset, ?selftest
  db.js          DuckDB-WASM worker, ensureTable(lang), query(sql, params)
  sql.js         WHERE-clause builders, ORDER BY, tokeniser, accent folding
  i18n.js        tr(), colLabel(), applyStatic(), 'langchange' event
  router.js      hash ⇄ tab, panel visibility
  facets.js      one facet row: label + Tom Select multi-select + AND | OR
  search_cv.js   controlled-vocabulary tab controller (cascade + paging)
  search_kw.js   keyword tab controller
  results.js     results toolbar, table or record list, summarised cells, paging
  detail.js      selected-record table with tooltip labels
  links.js       rebuilds the link chips from access_urls / access_labels
  tooltips.js    tippy.js initialisation
  markdown.js    fetch + render + table of contents for the two markdown tabs
  visualize.js   Visualize tab: selectors, chart, CSV and PNG downloads
  barchart.js    the bar chart as plain SVG, and its PNG export
  util.js        escapeHtml, listToArray, staleGuard, el(), downloadBlob
  styles/        base.css (replaces Bootstrap/reactable), portal.css (port of custom.css)
```

Typography follows treatment A ("Catalogue") from the design review: record
titles, the site title and headings are set in Source Serif 4, and everything
else in Source Sans 3. Both fonts are self-hosted through the `@fontsource`
packages imported at the top of `main.js` (no requests to Google), and the
two families are named once, as `--font-display` and `--font-ui` in
`base.css`.

Each file starts with a comment describing its role; the notes below cover
the logic that spans files.

### Search by Controlled Vocabulary

Five facets, each a row with the field name, a multi-select and an
AND | OR control, laid out in two columns: Subject, Name of Census and
Census Year(s) Covered by Item on the left; Geographic Units and Content Type
in a narrower column on the right.
An info glyph after a field name shows that field's definition on hover or
click; the text comes from `help_<field>` rows in
`prep/interface_elements.xlsx`, and a field without such a row gets no glyph.
`sql.buildCvWhere()` turns the selections into one `WHERE` clause:

- Facets are always combined with `AND`.
- Within a facet, AND | OR decides how several selected values combine.
  Four of the five columns are lists, so the clause is
  `list_has_all(col, [v1, v2])` (AND, the default) or
  `list_has_any(col, [v1, v2])` (OR). A single value always uses
  `list_has_any`. Name of Census is a scalar column and uses `IN (…)`.
- Values are bound as prepared-statement parameters (`?`), never spliced into
  the SQL text. Column and table names come from fixed lists.

Every change calls `refresh()` in `search_cv.js`, which issues seven queries
at once and waits for all of them:

| Query | Purpose |
|---|---|
| `SELECT DISTINCT UNNEST(col) AS val … WHERE <all facets> ORDER BY val` (×4) | the **cascade**: each dropdown only offers values that still occur under the current filter |
| `SELECT DISTINCT itemCensusName … WHERE <all facets except census name>` | census name excludes its own clause so more than one census can be picked |
| `SELECT COUNT(*) …` | the "Page x of y (n results)" text |
| `SELECT * … ORDER BY … LIMIT n OFFSET m` | the visible page |

Paging (‹ › and rows per page) re-runs only the last two.

Results are sorted by the first entry in Census Year(s) Covered by Item,
then by title, with
undated items last.

Because queries are asynchronous, a fast second change could finish before a
slow first one. `util.staleGuard()` hands each `refresh()` a token; when the
results come back, a refresh that is no longer the latest simply discards
them. This replaces Shiny's reactive invalidation.

### Search by Keyword

The text box is committed on Enter or the Search button; AND | OR is read
live, so switching it re-runs the last search immediately.

`sql.tokenise()` splits the text in two passes: anything in quotes
(`"…"`, `'…'`, `«…»`) is one phrase; the rest is split on spaces and commas.

Keywords are matched against one pre-built column, `search_text`: the title,
subjects, geographic coverage and geographic units of each record,
lower-cased, accent-folded and joined with a control character so a term
cannot match across two fields. `db.ensureSearchText()` adds the column to a
language's table the first time keyword search needs it, in about 0.2 s; it
starts in the background when the keyword tab is opened or the language is
switched there. For each term `sql.buildKwWhere()` then produces

```sql
search_text LIKE '%' || ? || '%'
```

and the term clauses are joined with `AND` (every term must appear) or wrapped
in one `OR` group (any term). A search takes a few milliseconds instead of the
second or more it took when every row was folded on every query. Accent
folding uses a fixed 17-pair table (é è ê ë → e, ç → c, œ → oe, …) applied
identically to the typed term in JavaScript and to the column in SQL, so
`donnees` and `données` return the same rows. The results are identical to
the R app's per-field test, which the `?selftest` page checks. There is no
full-text index or ranking; this is a substring match, as in the R app.

### Results and detail view

`results.js` draws the current page under a toolbar that shows the record
count, the sort order, rows per page (25 by default) and paging; a second
pager follows the results when there is more than one page. Columns are the
ones flagged `visible_results` in `prep/namestable.xlsx` (passed through
`meta.json`), and both search tabs show the same columns. Census Year(s)
Covered by Item is shortened to "Years Covered" in the table header only.
The table always fits its box: `WIDTHS` in `results.js` gives each column a
relative share (Title and Name of Census the largest, and equal), the shares
of the visible columns are scaled to 100% in a `<colgroup>`, and
`table-layout: fixed` keeps them, so columns shrink proportionally and their
contents wrap. Below 1200 px, where some words are wider than their column,
cells other than titles hyphenate in the page's language; link chips break at
the dots of their host names instead.

Long list cells are summarised so that one record cannot fill the screen:
years covered show as a range ("1665-6 → 1870-71") with "See all years", and other lists
show their first two values and "+19 more" (formats show up to five). The
buttons expand the cell in place. Every value is HTML-escaped. `links.js`
rebuilds the Links column as `<a class="accessbutton">domain</a>` chips side
by side; several links to the same site share one chip with a count, which
opens to list them.

Below 900 px wide the table becomes a list of records: the title, the link
chips, one wrapping line of details and the subject tags.

Clicking a title runs `SELECT * FROM inventory_<lang> WHERE id = ?` and
`detail.js` swaps the results for a two-column table: one row for every
column flagged `visible_detail` that has a tooltip definition (25 fields), in
database order. The field label carries its definition in
`data-tippy-content`, which `tooltips.js` turns into a tippy.js popup. The
"Back to Results" button restores the results without re-querying.

### Visualize

The chart does not query the database. `viz_counts.json` holds counts that
were aggregated in R by `prep_db.R`, as compact rows
`[year, attributeKey, value, count]` under `yearPub` (by year of publication)
and `yearCov` (by year covered), per language. Choosing an attribute fills
the item dropdown with the distinct values seen for it; choosing an item
draws a bar chart of count by year, styled after the original ggplot
(`#0b5394` bars, bold blue title, boxed axes with gridlines, vertical year
labels; every label is shown unless they would overlap). `barchart.js` draws
it as plain SVG sized to the window, with a hover label for each bar; it
replaced Plotly, which was 377 KB compressed for this one chart. "Download
the data" writes the plotted rows as CSV with the same bilingual headers the
Shiny app used; "Download the chart" renders the same chart at 1920×720 and
saves it as a PNG.

### Documentation and About

`markdown.js` fetches `doc_{en,fr}.md` and `about_{en,fr}.md` from the
[census-recensement/portal](https://github.com/census-recensement/portal)
repository at view time, exactly as the Shiny app did, renders them with
`marked`, gives every `h2`/`h3` an id, and builds the sticky table of
contents pinned to the right (a port of `inject_toc()` in `R/mod_markdown.R`).
Text under each heading is grouped and flows into two columns when the page
is wide enough; in the field descriptions, "Definition", "Notes" and "Values"
become small labels with their text directly underneath.
Rendered pages are cached per language for the session. TOC links scroll
within the page rather than changing the hash, because the hash is the tab
router's state. If the fetch fails, a bilingual "content unavailable" message
is shown.

### Language switching

The EN/FR switch in the header:

1. uses the other language's table, which is normally already built: once
   the engine is ready and the browser is idle, `main.js` downloads and builds
   it in the background (skipped when the visitor has turned on data saving).
   If it is not ready yet, the overlay reappears with download progress;
2. calls `i18n.setLang()`, which stores the choice, refreshes every
   `data-i18n` / `data-i18n-col` node, and dispatches a `langchange` event;
3. each tab module listens for that event and starts over against the other
   table (`inventory_fr` ⇄ `inventory_en`).

Facet values, keyword hits and chart items are language-specific, so the
search tabs and the Visualize tab clear their selections on a switch rather
than carrying over values that would match nothing.

### Differences from the Shiny app

Intentional:

- Cell text is HTML-escaped. The Shiny tables rendered values as HTML, which
  swallowed titles such as `<25 Years by Age`.
- Switching language clears the current filters instead of keeping
  now-meaningless selections.
- Link hrefs are the raw URLs from `itemAccess`; the old pre-rendered HTML had
  URL-decoded them.
- Row hover highlight is done in CSS instead of reactable.
- The layout was compacted after a design review: one masthead for title,
  tabs and language; field labels beside their boxes with AND | OR in place
  of the AND/OR switches; a results toolbar; summarised list cells; 25 rows
  per page by default; one accent colour; the footer at the end of the page.
- Results are sorted by the first year covered rather than by year of
  publication.

Unchanged: SQL semantics (checked by `prep_db.R` on every run and by the
`?selftest` page), page-size options, tooltip text, chart data.

## Update the data

The data files in `public/data/` are produced by `prep/prep_db.R`, in the
`prep` folder next to this repository:

```
census_inventory_portal/
  prep/          prep_db.R and the Airtable exports
  portal-wasm/   this repository
```

1. Export the English and French tables from Airtable into `prep/` as
   `airtable_en.csv` and `airtable_fr.csv`.
2. If the web app itself changed, update `app_version` and `app_date` in the
   settings block at the top of `prep_db.R`. The database date is set to the
   day the script runs. All three appear in the site footer.
3. Run the script from the `prep` folder (open `prep.Rproj`, then):

   ```r
   source("prep_db.R")
   ```

   It writes `inventory_dat.csv` and `db_export.csv` into `prep/`, and the
   parquet files, `meta.json`, `viz_counts.json`, the two snapshots and
   `selftest.json` into
   `../portal-wasm/public/data` (set `PORTAL_WEB_DATA` to write elsewhere).
   It stops with an error if any of its test searches return different
   results from the parquet than from the source table.
4. Commit the changed files in this repo and push `main`. The GitHub Actions
   workflow rebuilds and deploys the site within a few minutes. Open the site
   with `?selftest` to repeat the test searches in the browser.

The retired Shiny app's export lives in `prep/old_versions/export_shiny.R`
and is not needed for this site.

## Deploy

`.github/workflows/deploy.yml` runs on every push to `main`: `npm ci`,
`npm run build`, then `actions/deploy-pages`. The repository's Pages source
is set to "GitHub Actions". The parquet files are committed directly (they
are small, and Pages cannot serve Git LFS objects). GitHub Pages compresses
the self-hosted assets with gzip; the app fetches data files with
`cache: 'no-cache'` so a data update is picked up on the next visit.
